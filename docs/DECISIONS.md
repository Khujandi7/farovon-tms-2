# FAROVON TMS 2.0 — принятые решения (Phase 1 и 1.5)

Дата фиксации: 04.10.2026. Подтверждено владельцем проекта.

## D1. Источник истины
PostgreSQL (Supabase) — единственный источник истины. Excel и Google Sheets — только источники импорта.
Финансовые расчёты, курсы, KPI и агрегаты считаются детерминированно в PostgreSQL/на сервере.

## D2. ИИ
ИИ может: анализировать, объяснять, рекомендовать, искать аномалии, помогать пользователю.
ИИ не может самостоятельно: изменять финансовые значения, удалять данные, объединять сотрудников,
изменять бюджет, подтверждать спорные записи. Любое предложение ИИ подтверждает человек.

## D3. История миграций
Локальные файлы названы по версиям, уже записанным в Supabase. История в Supabase не меняется,
`supabase migration repair` не используется. Содержимое миграций Phase 1 (0001–0004) не меняется.
`apply_migration` (MCP) присваивает свою версию — после применения локальный файл называется по ней.

## D4. Финансовый факт и KPI (функция `kpi_year(год)`)
| | Определение |
|---|---|
| A. Financial actual | сумма `expense_operations.amount_tjs`, не сторно; год по `operation_date`; статус тренинга не важен (расходы CANCELLED/POSTPONED входят) |
| B. Delivered | тренинги `COMPLETED`, не в архиве; год по `start_date`; уникальные участники и человеко-часы только по ним |
| C. In progress | тренинги `IN_PROGRESS` — отдельный показатель |
| D. Unplanned delivered | `UNPLANNED` + `COMPLETED`; доля от B; неподтверждённые кандидаты отдельно |
| E. Unplanned financial actual | расходы по тренингам `UNPLANNED`, тот же год-базис, что у A |

Отклонение = A − план. Статус плана: `OK`, `NO_APPROVED_VERSION`, `NO_FX`. Старые функции
`variance_tjs`, `saving_*`, `utilization_percent`, `unplanned_stats` помечены DEPRECATED; интерфейс использует `kpi_year`.

## D5. Финансовая видимость
HR (и пользователь без профиля / неактивный) получает `NULL` и `financial_access = FINANCIAL_DATA_RESTRICTED`.
`0` означает только «расходов действительно нет». Интерфейс не приводит `NULL` к 0.

## D6. Расходы
Физическое DELETE запрещено. Ошибочная операция сторнируется: `void_expense(id, причина)` (ADMIN, FINANCE).
Сторно необратимо, сторнированная строка неизменяема.

## D7. Бюджет
APPROVED-версия неизменяема (версия, строки, статьи). Изменение: `create_budget_revision(версия, причина)` →
правка DRAFT → `approve_budget_version(DRAFT)`: прежняя APPROVED становится ARCHIVED в той же транзакции.
Удалять можно только DRAFT. Импорт бюджета тоже идёт через DRAFT → approve.

## D8. Тренинги
Удаление — архив `archive_training(id, причина)`; FK RESTRICT на расходы, участников и сессии.
Тренинг с расходами архивировать нельзя: он получает статус CANCELLED/NOT_HELD, расходы остаются фактом.
CANCELLED/NOT_HELD — бизнес-статусы, а не удаление.

## D9. Тренинги №7 и №8 (Реестр)
Один проведённый тренинг, две сессии: 13–16.07.2025 и 23–26.07.2025.
50 уникальных участников, расход 121 085 TJS, 2 421,70 TJS на человека, 800 человеко-часов.
Существующие данные не меняются. При импорте обязательно проверить реальное распределение участников
между двумя сессиями (800 = 50 × 16 верно, только если каждый был на одной сессии).

## D10. Обратная связь
Личность респондента — в `feedback_respondents` (прямой доступ закрыт всем).
ADMIN и ACADEMY_MANAGER раскрывают личность через `reveal_respondent(id, причина)`; каждое раскрытие — запись `REVEAL` в `audit_log`.
Сырые ответы и комментарии видят только ADMIN и ACADEMY_MANAGER.
HR, FINANCE, VIEWER видят только агрегаты `feedback_summary()`; при числе ответов меньше 5 (`feedback_min_group`) — пусто.

## D11. Auth
Email + пароль. Публичная регистрация OFF. Anonymous sign-in OFF. Пользователей создаёт/приглашает только ADMIN
(серверный код с service_role; ключ никогда не в браузере). Роль никогда не берётся из `user_metadata`.
Неактивный пользователь (`profiles.is_active = false`) теряет доступ сразу.
Первый ADMIN: создать пользователя в Authentication → Users, затем один раз `select bootstrap_first_admin('email','ФИО')`
в SQL Editor. Последнего активного ADMIN нельзя понизить, деактивировать или удалить.

## D12. Пользователи и роли (Phase 2.2)
Только по приглашению: ADMIN вводит email, ФИО и роль → Auth Admin API `inviteUserByEmail()` → ADMIN (своей сессией, под RLS
`profiles_write` и аудитом) создаёт строку `profiles`. Не создался профиль — только что созданный пользователь Auth удаляется.
Временных паролей нет: ссылка из письма → `/auth/confirm` (`verifyOtp(token_hash, type)`, типы только `invite`/`recovery`)
→ `/auth/set-password`, пароль ≥ 12 символов. Забытый пароль — самостоятельно (`/forgot-password`, ответ не раскрывает наличие email)
или ссылкой от ADMIN. Свой пароль пользователь меняет в Настройках (нужен текущий пароль).
`service_role` используется только для Auth Admin API (приглашение, блокировка, email/даты входа) и только в серверном коде
(`server-only`); запись в таблицы — сессией ADMIN, иначе `audit_log.user_id` был бы NULL. Роль всегда из `app_role()`.
Деактивация: `profiles.is_active = false` (доступ закрыт сразу) + блокировка входа в Auth (`ban_duration`), восстановление — наоборот.
Защита в БД (M9 `profiles_self_protect`, P0011): никто, включая ADMIN, не меняет себе `role`/`is_active` и не удаляет свой профиль;
`profiles_guard` (P0003) по-прежнему не даёт убрать последнего активного ADMIN. Не блокируются SQL Editor, service_role и
`bootstrap_first_admin()` (там `auth.uid()` = NULL). Те же правила дублируются в приложении (понятные сообщения).
