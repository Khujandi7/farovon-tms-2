# FAROVON TMS 2.0 — принятые решения (Phase 1 и 1.5)

Дата фиксации: 04.10.2026. Подтверждено владельцем проекта.

## D1. Источник истины
PostgreSQL (Supabase) — единственный источник истины. Excel и Google Sheets — только источники импорта.
Финансовые расчёты, курсы, KPI и агрегаты считаются детерминированно в PostgreSQL/на сервере.

## D2. ИИ
ИИ может: анализировать, объяснять, рекомендовать, искать аномалии, помогать пользователю.
ИИ не может самостоятельно: изменять финансовые значения, удалять данные, объединять сотрудников,
изменять бюджет, подтверждать спорные записи. Любое предложение ИИ подтверждает человек.

## D3. История миграций
Локальные файлы названы по версиям, уже записанным в Supabase. История в Supabase не меняется,
`supabase migration repair` не используется. Содержимое миграций Phase 1 (0001–0004) не меняется.
`apply_migration` (MCP) присваивает свою версию — после применения локальный файл называется по ней.

## D4. Финансовый факт и KPI (функция `kpi_year(год)`)
| | Определение |
|---|---|
| A. Financial actual | сумма `expense_operations.amount_tjs`, не сторно; год по `operation_date`; статус тренинга не важен (расходы CANCELLED/POSTPONED входят) |
| B. Delivered | тренинги `COMPLETED`, не в архиве; год по `start_date`; уникальные участники и человеко-часы только по ним |
| C. In progress | тренинги `IN_PROGRESS` — отдельный показатель |
| D. Unplanned delivered | `UNPLANNED` + `COMPLETED`; доля от B; неподтверждённые кандидаты отдельно |
| E. Unplanned financial actual | расходы по тренингам `UNPLANNED`, тот же год-базис, что у A |

Отклонение = A − план. Статус плана: `OK`, `NO_APPROVED_VERSION`, `NO_FX`. Старые функции
`variance_tjs`, `saving_*`, `utilization_percent`, `unplanned_stats` помечены DEPRECATED; интерфейс использует `kpi_year`.

## D5. Финансовая видимость
HR (и пользователь без профиля / неактивный) получает `NULL` и `financial_access = FINANCIAL_DATA_RESTRICTED`.
`0` означает только «расходов действительно нет». Интерфейс не приводит `NULL` к 0.

## D6. Расходы
Физическое DELETE запрещено. Ошибочная операция сторнируется: `void_expense(id, причина)` (ADMIN, FINANCE).
Сторно необратимо, сторнированная строка неизменяема.

## D7. Бюджет
APPROVED-версия неизменяема (версия, строки, статьи). Изменение: `create_budget_revision(версия, причина)` →
правка DRAFT → `approve_budget_version(DRAFT)`: прежняя APPROVED становится ARCHIVED в той же транзакции.
Удалять можно только DRAFT. Импорт бюджета тоже идёт через DRAFT → approve.

## D8. Тренинги
Удаление — архив `archive_training(id, причина)`; FK RESTRICT на расходы, участников и сессии.
Тренинг с расходами архивировать нельзя: он получает статус CANCELLED/NOT_HELD, расходы остаются фактом.
CANCELLED/NOT_HELD — бизнес-статусы, а не удаление.

## D9. Тренинги №7 и №8 (Реестр)
Один проведённый тренинг, две сессии: 13–16.07.2025 и 23–26.07.2025.
50 уникальных участников, расход 121 085 TJS, 2 421,70 TJS на человека, 800 человеко-часов.
Существующие данные не меняются. При импорте обязательно проверить реальное распределение участников
между двумя сессиями (800 = 50 × 16 верно, только если каждый был на одной сессии).

## D10. Обратная связь
Личность респондента — в `feedback_respondents` (прямой доступ закрыт всем).
ADMIN и ACADEMY_MANAGER раскрывают личность через `reveal_respondent(id, причина)`; каждое раскрытие — запись `REVEAL` в `audit_log`.
Сырые ответы и комментарии видят только ADMIN и ACADEMY_MANAGER.
HR, FINANCE, VIEWER видят только агрегаты `feedback_summary()`; при числе ответов меньше 5 (`feedback_min_group`) — пусто.

## D11. Auth
Email + пароль. Публичная регистрация OFF. Anonymous sign-in OFF. Пользователей создаёт/приглашает только ADMIN
(серверный код с service_role; ключ никогда не в браузере). Роль никогда не берётся из `user_metadata`.
Неактивный пользователь (`profiles.is_active = false`) теряет доступ сразу.
Первый ADMIN: создать пользователя в Authentication → Users, затем один раз `select bootstrap_first_admin('email','ФИО')`
в SQL Editor. Последнего активного ADMIN нельзя понизить, деактивировать или удалить.

## D12. Пользователи и роли (Phase 2.2)
Только по приглашению: ADMIN вводит email, ФИО и роль → Auth Admin API `inviteUserByEmail()` → ADMIN (своей сессией, под RLS
`profiles_write` и аудитом) создаёт строку `profiles`. Не создался профиль — только что созданный пользователь Auth удаляется.
Временных паролей нет: ссылка из письма → `/auth/confirm` (`verifyOtp(token_hash, type)`, типы только `invite`/`recovery`)
→ `/auth/set-password`, пароль ≥ 12 символов. Забытый пароль — самостоятельно (`/forgot-password`, ответ не раскрывает наличие email)
или ссылкой от ADMIN. Свой пароль пользователь меняет в Настройках (нужен текущий пароль).
`service_role` используется только для Auth Admin API (приглашение, блокировка, email/даты входа) и только в серверном коде
(`server-only`); запись в таблицы — сессией ADMIN, иначе `audit_log.user_id` был бы NULL. Роль всегда из `app_role()`.
Деактивация: `profiles.is_active = false` (доступ закрыт сразу) + блокировка входа в Auth (`ban_duration`), восстановление — наоборот.
Защита в БД (M9 `profiles_self_protect`, P0011): никто, включая ADMIN, не меняет себе `role`/`is_active` и не удаляет свой профиль;
`profiles_guard` (P0003) по-прежнему не даёт убрать последнего активного ADMIN. Не блокируются SQL Editor, service_role и
`bootstrap_first_admin()` (там `auth.uid()` = NULL). Те же правила дублируются в приложении (понятные сообщения).

## D13. Обучения, заявки, редактирование и аудит (Phase 3A)
Принцип: VIEW → OPEN → EDIT → VALIDATE → SAVE → AUDIT → RECALCULATE. Данные исправляются в интерфейсе там, где это разрешено ролью;
вся бизнес-логика — в RPC PostgreSQL (`create_training`, `update_training`, `upsert_session`, `add_participants`, `set_attendance`,
`add_expense`, `link_request` …), серверные действия Next.js — тонкие обёртки под сессией пользователя (не service_role).
Роли: тренинги и заявки — ADMIN, ACADEMY_MANAGER; участники и посещаемость — + HR; расходы — ADMIN, ACADEMY_MANAGER, FINANCE
(аннулирование — только ADMIN, FINANCE); сотрудники и подразделения — ADMIN, ACADEMY_MANAGER, HR; Data Quality — ADMIN, ACADEMY_MANAGER;
чтение — по прежней матрице (HR не видит суммы).
Существенные изменения (деньги, статус, даты, часы, заявка, посещаемость, связи) требуют `reason` (P0012); причина пишется в `audit_log.reason`
через `app.change_reason`. Откат (`revert_change`) покрывает тренинги, заходы, участников, посещаемость, заявки; расходы — только аннулированием.
Конфликт при откате (запись изменилась позже) — P0014. Сотрудники не создаются из участников автоматически: это отдельный справочник.
Человеко-часы: по посещаемости, если она ведётся (`has_attendance`), иначе прежнее правило (регрессия #7+#8 = 50 участников, 800 ч, 121 085 TJS).
Даты и часы тренинга с заходами считаются по заходам (P0013). Суммы расходов при изменении числа участников не пересчитываются.
Валюта: исторические USD остаются USD с реальным курсом; новые заявки — только TJS. Data Quality — правила `dq_scan()` с действиями
Открыть / Исправить / Выбрать / Связать / Оставить на проверке; исправленные данные закрывают замечание при следующей проверке.
Импорт Google Sheets (Phase 3B) не входит в 3A и подключается после получения реальных заголовков.

## D14. Learning & Employee Dossier (Phase 3A.1)
Learning Event — это расширенная таблица `trainings` (тип из справочника `learning_event_types`, ADMIN добавляет типы в UI), а не отдельные
таблицы семинаров/форумов/конференций: заходы, участники, посещаемость, расходы, заявки, аудит, откат и DQ переиспользуются. KPI «проведено
обучений» считает только групповые типы (`is_group`), индивидуальное обучение — отдельная сумма; определения KPI не менялись.
Lifecycle — расширение enum `training_status` (DRAFT, APPROVED, REGISTERED); ARCHIVED — прежний `archived_at`. Переходы проверяет триггер БД
(`training_transition_allowed`, P0016), ADMIN может исправить любой переход с причиной.
Экзамены — отдельная сущность (одна строка = одна попытка, история не перезаписывается); стоимость экзамена — `exam_costs` (видят только
ADMIN/ACADEMY_MANAGER/FINANCE, FX как у расходов). Сертификаты — статус вычисляется (ACTIVE/EXPIRED/REVOKED/NO_EXPIRATION). Навыки — append-only
история. План развития — `development_goals`.
Финансирование: `funding_policies` (+ исходы PASSED/FAILED → % ответственности сотрудника) настраиваются и подтверждаются FINANCE/ADMIN;
подтверждённая политика неизменяема. Обязательство создаёт только `evaluate_agreement` при подтверждённой действующей политике, договоре и
известном результате; затем человек делает `review_obligation`. Никаких удержаний из зарплаты и payroll; UI показывает «Требуется проверка
ответственным сотрудником».
Документы — метаданные в `documents`, файлы в приватном бакете `tms-documents`; загрузка под сессией пользователя в заранее
зарегистрированный путь, чтение — только signed URL (60 с), удаления нет (архив). Финансовые типы — только ADMIN/ACADEMY_MANAGER/FINANCE.
Публичный портал: аноним не получает доступа к таблицам; серверное действие вызывает две функции, выданные только service_role
(`public_request_options`, `submit_public_request`), с honeypot, HMAC-хэшем клиента и лимитами в БД (5/ч на клиента, 30/ч на ссылку).
Подразделение заявки берётся из токена; переименование не ломает ссылку, деактивация закрывает её.
Импорт: общий конвейер `import_jobs`/`import_job_rows` (stage → решения → commit одной транзакцией), lineage в `source_files/source_records`;
сотрудники из участников не создаются никогда. Google Sheets — через вставку/CSV до Phase 3B (Service Account).

## D15. Сквозной жизненный цикл (Phase 3A.2)

Обучение — центральное рабочее место; все модули связаны через `training_id` и сотрудника. Тренеры — существующие `trainers`/`training_trainers`
с ролью PRIMARY/CO (один основной), без дубликатов (уникальный `norm_name`). Обратная связь связана с обучением через приглашения участникам;
итог — веса 40/40/20 из `app_settings` с перераспределением при отсутствии блока, порог анонимности Phase 1.5 сохраняется. Отчёты и дашборд
используют одни функции (`lifecycle_kpis` согласована с `kpi_year`). Миграция M21 аддитивна, ни одна функция прежних фаз не переопределена.
Подробно: `docs/PHASE_3A2_DECISIONS.md`, `docs/PHASE_3A2_INTEGRATION_AUDIT.md`, `docs/PHASE_3A2_DATA_FLOW.md`.

## D16. Google Sheets и выбор участников (Phase 3B)

Google Sheets — ещё один источник существующего конвейера импорта (`import_stage/import_commit`, сопоставление, lineage), а не параллельная система.
Доступ — сервисный аккаунт, только чтение, только на сервере (JWT, `GOOGLE_SERVICE_ACCOUNT_JSON`); пользовательский OAuth не нужен. Колонки источника хранятся по
названию. Отсутствующие в таблице сотрудники не удаляются: флаг + замечание DQ + авто-закрытие при возвращении. Нового расписания/cron нет (ручной «Синхронизировать сейчас»).
Участники — существующие `training_participants` (снимок подразделения), создаются только из справочника; `create_training_with_participants` — одна транзакция поверх
`create_training` + `add_participants`. План по заявке — контрольная цифра, факт — выбранные сотрудники. M22 аддитивна.
